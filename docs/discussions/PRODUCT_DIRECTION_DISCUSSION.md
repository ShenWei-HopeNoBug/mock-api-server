# 产品定位与迭代方向讨论报告

> 讨论日期：2026-11-07
> 参与者：项目作者 × Devin
> 性质：思维碰撞记录，非实施承诺；后续结论若立项实施，以 `plans/` 正式方案为准

## 1. 现状功能盘点

本项目是一条完整的「录制 → 存储 → 管理 → 回放」流水线：

| 环节 | 实现 |
|---|---|
| 数据采集 | mitmproxy 正向代理抓包，`include_path` 过滤，自动录制 JSON 接口响应 + 静态资源 URL 清单 |
| 存储 | 工作目录隔离的 SQLite（schema 版本化迁移），`api_data` / `api_response_variants` / `static_data` 三表 |
| 管理 | ① PySide6 WebView 内嵌 Vue3 管理台（dataManager / apiTester / configEdit）② MCP 服务暴露 Agent 完整 CRUD 工具集 |
| 回放 | `/api` 前缀精确匹配（route+method+content_type+sorted params 的 md5）；`Mock-Server-Device-Id` 变体轮播 + 空闲超时重置；全局/单接口两级延时；静态资源 URL 本地化替换 + 批量下载 + 图片压缩；5 种静态资源限速策略 |

核心洞察：最大的独特性不是"抓包"本身，而是**录制天然保证了接口间的数据关联性**——列表接口返回的 id，就是详情接口响应里的那个 id。这是"造数据"路线（mockjs 家族）解决不了的问题。

## 2. 实际使用价值点（用户视角）

### 价值一：契约先行开发

非全栈分工场景下，后端出了接口协议但工期原因没发测试环境时，前端用本工具过渡。当前已跑通 **yapi → MCP → 在工作目录建 mock 数据** 的链路，开发体验顺滑。

> 评价：这是"契约先行"体验，业界正在往这个方向走（Apifox 等也在做 MCP），有先发优势但不算护城河。

### 价值二：故障复现与状态覆盖

- **线上低频问题复现**：录制接口数据的思路天然能稳定复现前端线上问题，对触发率极低的问题排查意义重大；
- **难触发状态机覆盖**：前端 UI 展示层的状态机依赖接口数据（如合成的 status：进行中/成功/失败），部分状态在测试和生产环境很难触发导致 case 覆盖面不足，用本工具造对应数据可在开发阶段测试这些 case。

> 评价：这是真正的差异化。工具的本质从"mock 工具"演进为**开发期故障注入 / 状态覆盖率工作台**——录制的真实流量是线上 bug 的"案发现场快照"，变体系统是状态机的可编程遍历器。

## 3. 业界方案对比

### 3.1 造数路线：Mock.js / faker / MSW / json-server / vite-plugin-mock

- **它们**：前端代码内或 dev server 层拦截，靠 schema/模板生成假数据。上手极快；数据彼此孤立（列表 id 与详情 id 对不上），无状态、无持久化。
- **本项目优势**：真实数据、接口间关联性、持久库、GUI。
- **本项目劣势**：它们是"代码即配置"，能进 git、随项目走；MSW 可 dev/test 复用同一套 handler。本项目是黑盒工具 + 本地 db，团队无法共享同一份基线数据。

### 3.2 桌面 GUI 工具：Mockoon / Reqable

Mockoon 是最像的竞品：路由配置、任意 method/状态码/header、handlebars templating、proxy mode（命中走 mock、未命中回源）、环境文件可分享。

- **本项目优势**：录制全自动（流量过代理即入库，无需先配路由）；参数级精确匹配是数据维度（Mockoon 规则匹配要手配）；变体轮播、静态资源本地化无对应物；MCP 是全新维度。
- **本项目劣势**：协议能力被碾压——只支持 GET/POST、固定 200 + jsonify、不能自定义 header/非 JSON body；无 templating（响应不能引用请求参数）；改数据需重启服务。

### 3.3 抓包+改包工具：Charles / Fiddler / Whistle / mitmproxy 本体

- **它们**：Map Local / rewrite 是"改包"思维——逐条手工映射响应到本地文件，无数据管理层级，录完是散落的规则。
- **本项目优势**：抓包结果结构化入库、可管理可排序可启停，带变体和静态资源闭环。"录制结果可运营" vs "录制结果是一次性规则"。
- **本项目劣势**：门槛不比它们低（都要 CA 证书+代理），它们还能兼顾改包调试；Whistle 配置语法陡但能力上限高。

### 3.4 平台全家桶：YApi / Apifox / Postman

- **它们**：接口契约文档 + mockjs 智能造数 + 云端 mock + 团队协作。Apifox"期望"能做参数匹配不同响应，但要手工逐条配。
- **关系判断**：**互补而非竞争**。YApi 管"契约"（接口应该长什么样），本工具管"真实数据快照"（接口实际返回过什么）。完全可以 YApi 看文档、本工具跑数据。
- **本项目劣势**：无团队协作、无导出分享；云端 mock 对移动端零配置（本工具要求手机配代理+装证书）。

### 3.5 录制回放专业户：WireMock / Hoverfly

业界唯一同思路。WireMock record & playback + Scenario 状态机（≈本项目的变体）+ fault injection，功能深度远超本项目，但 Java 后端测试导向、无 GUI（Cloud 版才有）、面向 API 测试而非前端开发。

### 3.6 差异点总表

| 能力 | 本项目 | 造数路线 | 桌面 GUI | 抓包改包 | 平台全家桶 | 录制回放 |
|---|---|---|---|---|---|---|
| 数据关联性（接口间字段一致） | ✅ 录制天然保持 | ❌ | ❌ | ❌ | ❌ | ✅ |
| 参数级匹配（同路由不同入参不同响应） | ✅ | ❌ | 🔸手配规则 | 🔸 | 🔸期望手配 | ✅ |
| 变体/状态机 | ✅ Device-Id 轮播 | ❌ | ❌ | ❌ | ❌ | ✅ Scenario |
| 静态资源本地化闭环 | ✅ | ❌ | ❌ | 🔸逐文件配 | ❌ | ❌ |
| MCP / Agent 工具面 | ✅ | ❌ | ❌ | ❌ | 🔸新兴 | ❌ |
| GUI + 结构化数据管理 | ✅ | ❌ | ✅ | 🔸 | ✅ | ❌ |
| 全 method/状态码/header | ❌ GET/POST+200 | 🔸 | ✅ | ✅ | ✅ | ✅ |
| 动态响应 templating | ❌ | ✅ | ✅ | 🔸 | ✅ | ✅ |
| 团队协作/数据分享 | ❌ | 🔸代码入库 | 🔸环境文件 | ❌ | ✅ | 🔸 |

**一句话结论**：业界要么"造数"（假但快），要么"改包"（真但散），要么"录制回放"（真但面向后端测试/无管理界面）。「录制结果结构化入库 + GUI 管理 + 变体/限速回放」这个组合是独一份，卡位在"前端开发要跑真实业务数据"的缝里。

## 4. 差异化定位结论

**定位叙事：mock 驱动的可复现测试工作台。** 核心故事是——"录一遍真实链路，得到一组互相自洽的 mock 数据，任何前端/真机环境都能离线跑；再叠加测试任务，把它变成可复现的故障注入与状态覆盖工具"。

**不建议**往 Apifox/Postman 全家桶方向走，资源耗不起且打不过；应把"真实数据录制回放"这条差异化路线做深。

## 5. 现存短板清单

按对用户价值的损害排序：

1. **GET/POST + 固定 200/JSON body**：PUT/DELETE/PATCH 没法 mock，无法模拟 4xx/5xx/自定义 header——硬伤，但改动小收益大；
2. **参数精确匹配的脆弱性**：录制的 params 含 timestamp/sign/token 时回放必然 miss——录制回放方案的通病，需要"忽略参数/参数白名单"消化；
3. **改 mock 数据需重启服务**：`mock_api_map` 只在启动时构建；
4. **录制入口单一**：仅正向代理抓包；纯 web 场景 HAR 导入门槛低得多；
5. **数据资产出不去**：SQLite 在本地，不能导出环境包给同事/git；
6. **抓包数据 `done()` 才批量入库**：中途崩溃全丢，长跑抓包有风险。

## 6. 迭代方向建议

### 第一层：补回放能力短板（地基）

- 全 HTTP method + 自定义 status/header/非 JSON body
- mock 数据热生效
- path pattern 匹配（`/user/{id}`）+ 忽略参数配置（消化 token/timestamp）
- 响应 templating：响应体允许 `{{params.id}}` 引用请求参数 + 内置 faker——"录一条、覆盖一类"

### 第二层：拓宽录制入口、强化关联性卖点（差异化）

- **反向代理模式**：前端直接指 mock server，未命中自动回源录制——"边用边录"，消除"先抓包再 mock"两步走（WireMock proxy+record / Mockoon proxy mode 已验证的顺滑工作流）；
- **HAR / fetch 日志导入**：覆盖不配代理的纯 web 场景；
- **关联性显式化**：录制后自动分析接口间字段引用（A 接口返回的 id 出现在 B 接口响应），可视化关联图，甚至"改一处、关联处自动跟着改"——把隐式优势变成可写进 README 的显性卖点，业界无人做；
- **场景包**：一次操作流程录制的数据打成命名快照，可切换、导出、分享——顺带解决数据资产流通。

### 第三层：顺着 MCP 和变体往前走（前瞻）

- 变体从"按 device 顺序轮播"演进为**显式状态机/条件变体**（第 N 次返回 A、之后返回 B；按入参条件选变体）；
- Agent 声明式搭场景（"给这个接口配 加载中→成功→失败 三种变体"）、在真实数据上推演补齐边界 case 变体——"AI 生成 mock"的正确姿势不是编假数据，而是在真实数据上推演。

### 远期 backlog

- **流量时序回放**：录制时保存同会话的请求时序，把真实 bug 会话的调用顺序和响应序列自动变成带时序的变体组——对"线上极低概率问题复现"是比手工组数据更狠的能力；
- **YApi 接入线**：团队在用 YApi 的前提下，「YApi 接口定义 → 自动生成骨架 mock → 录制数据填充」是接入团队工作流的最短路径（YApi 有开放 API/MCP 可拉接口定义）。

### 排序与范围纪律

- 第一层的 method/status/热更新是日常会撞上的痛点，先补；反向代理 + 忽略参数解决"录制回放可用性"；关联性显式化和场景包是真正拉开差距的东西，值得立项；
- 范围纪律：凡是需要 LLM 在场的环节不进本仓库，工具做数据与控制面，执行交给外部 Agent。
